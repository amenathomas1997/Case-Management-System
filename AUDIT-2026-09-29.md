# Code and WCAG audit — September 29, 2026

Scope: current working copy of the PHP web application, shared authentication, JSON API, styles, PDF generation, and selected iOS source. Existing modifications in `public/api.php` and `public/inc/core.php` were preserved. No application code was changed.

This is a source audit with isolated executable reproductions, not a complete production penetration test or WCAG conformance certification. Target: WCAG 2.2 Level AA. Database-backed workflows, browser rendering, assistive technology, and the native iOS app were not exercised end to end. Findings below distinguish executable evidence from source-level analysis.

Nine findings: three high priority (P1), six medium priority (P2).

## Code findings

### C1 — P1: Web equipment routes bypass caseload restrictions

Evidence: `public/equipment.php:44–50,68–73`. The inventory query returns every borrower's name and client ID. The return handler accepts any open loan ID and updates it without checking its client's assignment. Only the loan-out handler and client dropdown apply scope restrictions. The API already redacts other borrowers and scope-checks returns (`public/api.php:694–704,727–733`), making the web inconsistency explicit.

Reproduce with an equipment-enabled, own-caseload-only user: open Equipment while another employee's client has a loan. Their name and client link are exposed; “Mark returned” changes that client's loan. No forged request is needed.

Fix: redact out-of-scope borrower details and enforce `scope_check_client_id()` before returning a loan. Retain visibility of general inventory if that is the intended policy. Verify that both direct POSTs and displayed actions obey the same restriction.

### C2 — P1: Password reset does not revoke existing browser sessions

Evidence: `public/reset.php:37–44` updates the password and deletes API tokens/passkeys. `public/inc/bootstrap.php:145–184` continues accepting an existing verified session as long as its user is active; it never compares a credential/session version. Changing the password in `public/account.php` likewise only revokes mobile tokens.

Reproduce: sign in in browser A, reset the password through browser B, then request a protected page in A. Under this code, A remains authorized until idle expiry and can keep extending its session. A stolen browser session therefore survives account recovery.

Fix: persist an authentication version or session-revocation timestamp, capture it when establishing every session, and validate it on protected routes and keepalive/passkey session checks. Increment it on password reset and appropriate administrator recovery actions. Test web, SSO, passkey, and mobile entry points.

### C3 — P2: Spanish output translation silently changes submitted data

Evidence: `public/inc/bootstrap.php:47–52` runs `strtr()` over complete HTML, including attribute values and user-entered text. `public/community_referral.php:323` uses English service labels as checkbox values; line 106 intersects submitted values against those English strings.

Executable reproduction with the actual translation dictionary: `Job exploration counseling` becomes `Job exploration counseling (consejería de exploración de empleos)` inside the checkbox value. The server's intersection then accepts zero selections. A synthetic textarea containing `We need free software.` becomes `We need gratis software.`. This also means validation rerenders can alter user-entered text before resubmission.

Fix: translate individual interface labels at render time, preserve stable machine values, and never translate user content through a global response filter. Verify all five Pre-ETS choices in Spanish, including validation errors and resubmission.

### C4 — P2: A demoted administrator retains note-edit authority in an existing web session

Evidence: `public/inc/bootstrap.php:147,169–184` reads the live user but returns the role originally stored in the session. `public/client.php:61–62` allows editing another author's note when that stale role equals `admin`.

Reproduce: sign in as an administrator; from another administrator account, change that user's legacy role to instructor while leaving normal client access. The existing session can still edit notes authored by others on accessible clients. The API reads the live role, so behavior differs between clients.

Fix: refresh identity fields from the live row and make the note override use the intended effective permission policy consistently. Test demotion without signing the target user out first.

### C5 — P2: Concurrent loan requests can allocate the same equipment twice

Evidence: `public/equipment.php:31–37` and `public/api.php:712–720` perform an availability SELECT, INSERT a loan, and UPDATE status as separate operations. `schema_v4.sql` does not enforce one open loan per item.

Reproduce with two concurrent requests: both read Available before either updates it, both insert a loan, and both succeed. Returning either loan sets the item to Available while the other loan remains open. Partial database failures can also leave a loan and status inconsistent.

Fix: wrap allocation in a transaction and atomically claim Available status or lock the equipment row before checking it. Apply compatible locking to returns. Test two simultaneous allocations and a failure between writes; exactly one open loan should remain.

### C6 — P2: The My Account group editor can remove the last administrator

Evidence: `public/account.php:115–119` directly assigns a group without the self-demotion/last-administrator protections implemented in `public/users.php:78–90`.

Reproduce as the sole effective administrator: use My Account to assign yourself to a group without `admin`. Group permissions take precedence over the legacy role, so administration becomes inaccessible on the next request.

Fix: centralize the effective-administrator invariant and call it from every role/group mutation path, including this older account form. Verify that the final effective administrator cannot be removed, including concurrent changes.

## Accessibility findings

### A1 — P1: A failed keepalive request creates a keyboard trap

Evidence: `public/inc/layout.php:156–178`. While the timeout warning is open, Tab and Shift+Tab are always redirected to “Stay signed in.” Escape retries the network request. A rejected request is swallowed by an empty catch; there is no local dismiss action.

Executable reproduction: extracted the actual timeout JavaScript, substituted its PHP timer value, and ran it in Node with a minimal DOM and a rejected fetch. After Escape and Tab: dialog remained open, focus remained on `tw-stay`, and both keys were prevented. This is isolated event-handler evidence, not a browser/screen-reader run.

Impact: a keyboard user who loses connectivity cannot return to their form to recover unsaved text. This violates [WCAG 2.1.2, No Keyboard Trap (A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html).

Fix: provide a keyboard-operable local dismissal/recovery path independent of network success, restore focus, and expose the request failure. Test rejected, stalled, successful, and expired-session responses. Also verify focus containment after the expired-session state hides the stay button.

### A2 — P2: Generated PDF documents lack semantic structure and document language

Evidence: `public/invoice_pdf.php:89` creates an FPDF-derived document; `public/outcomes.php:115` uses FPDF directly. The bundled writer's catalog (`public/inc/fpdf/fpdf.php:1865`) emits no structure tree or document language. Tables are painted with cells rather than tagged table/header relationships.

Executable reproduction: a synthetic document generated with the bundled FPDF contained no `/StructTreeRoot`, `/MarkInfo`, or `/Lang`. No real client information was used. The invoice subclass overrides footer/layout helpers, not this document metadata/structure behavior.

Impact: standalone exports do not encode table relationships or a default reading language. Relevant criteria: WCAG 1.3.1 (A) and 3.1.1 (A). W3C documents [PDF table semantics](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF6) and [PDF document language](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF16).

Fix: generate tagged PDFs with language, headings, table headers, and reading order, or provide an explicitly identified, fully equivalent accessible alternative. Inspect representative multi-page outputs with a PDF accessibility checker and screen reader; HTML tables elsewhere do not automatically make standalone exports conformant.

### A3 — P2: Spanish pages leave English interface phrases without language markup

Evidence: `public/inc/bootstrap.php:51` changes the document language to Spanish. The dictionary does not translate the shared “Larger text,” “Display preferences,” or “Skip to main content” strings, and `public/inc/layout.php:38–44` provides no English language override. Theme button JavaScript also writes English labels.

Impact: assistive technology inherits Spanish for these English phrases. Relevant criterion: [WCAG 3.1.2, Language of Parts (AA)](https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html).

Fix: localize shared controls and their dynamically generated names, or explicitly mark retained English content with `lang="en"`. Verify the initial page and every theme-button state in Spanish.

## Verification and coverage limits

- PHP syntax validation: 81 files checked across `public/`, PHP cron jobs, and `dist/install.php`; zero syntax failures.
- Executed focused reproductions for translated form values/user text, timeout-dialog rejected-fetch behavior, and bundled PDF metadata/structure.
- Authorization, session invalidation, concurrency, and administrator-lockout findings were traced through source; they were not exercised against a live database.
- Existing positive patterns include prepared statements, shared CSRF protection on conventional web forms, explicit labels, skip navigation, visible focus styling, scoped checks on many client routes, and focusable table-scroll regions. These do not establish overall conformance.
- Still required for a full WCAG evaluation: authenticated browser tests across roles, keyboard and screen-reader workflows, light/dark contrast measurements including custom branding, 320-CSS-pixel reflow, 200% text resizing, 400% zoom, text-spacing overrides, validation and timeout states, and actual exported documents.
- Native iOS needs VoiceOver, Switch Control, external-keyboard, and Dynamic Type testing. The signature sheet's fixed-height drawing area and non-scrolling layout merit device testing; no formal native conformance conclusion is made here.
- The staged `dist/cms_dist/` copy was inventoried but not independently audited as a release artifact. Rebuild and verify distributions after fixes.

Recommended order: address C1, C2, and A1 first; then translation/data integrity, permissions consistency, loan transactions, administrator protection, and document/language accessibility. Run the live-role and assistive-technology checks before asserting WCAG 2.2 AA conformance.
