# Code audit, October 18, 2026 (second audit, after 4.27.0)

**Scope:** the whole system, after 4.27.0. That covers the website (PHP and MariaDB), the scheduled jobs and installer, the app API, and the iPhone and Android apps. Ten auditors each took one part. Two of them reviewed only the 4.27.0 changes, since new code is where new bugs are most likely. All work was read-only. Each finding was traced through the code, and the most important ones were reproduced on a scratch database.

**Result:** no High findings. There are 16 Medium findings after duplicates are merged, and about 70 Low.
- Caseload limits held everywhere except one report (N11).
- The 4.27.0 fixes held, with a few gaps, listed below.

The full findings for each area, with file and line, are in the appendix.

## Medium

1. **N1 Microsoft auto-provisioning admits guest accounts.** When "Automatically create accounts" is on, a B2B guest in the tenant gets a new staff account. This skips the 4.27.0 members-only rule (sso.php).
2. **N2 iPhone: offline entries over 30 days old are deleted after an upload that never reached the server.** This happens with no signal, a server error or a redirect (API.swift flushQueue).
3. **N3 iPhone: reminders, the widget and Siri use every session the account can see.** A director gets reminders for other staff members' sessions. The widget and Siri count them too.
4. **N4 Retries after a lost reply create duplicates.** No retry key is used on many create and send actions in both apps and the API:
   - send_report, schedule_session and save_client
   - incidents, homework and assessments
   - cohorts, contracts and device requests
   - and others

   The 4.27.0 claim that "retries never repeat" covered only signatures, releases, messages and queued entries.
5. **N5 Spanish in-person signing in both apps.** Instructions, the name field, the buttons and the errors are read with the English voice. Only the document is marked Spanish.
6. **N6 Android: open dialogs are lost when the phone rotates, the text size changes or the app process ends.** This affects completing a session (hours, note and the client's signature), incidents, lending, follow-ups, tasks, homework and the voice confirmation.
7. **N7 Changing a client's counselor rewrites the Bill-to on every draft invoice.**
   - The agency billing address is dropped.
   - Private-pay drafts are re-addressed to the counselor.
   - The API version includes an unconfirmed email.

   This happens in counselors.php, client_edit.php and api.php.
8. **N8 The staff compliance spreadsheet has no formula guard.** A staff member's credential name runs as a formula in the administrator's download. write_csv_row() does not apply csv_cell().
9. **N9 Editing a track has no stale-form check.** An old form reverses someone else's authorization change and re-prices logs.
10. **N10 Worksite assessment saves overwrite each other**, on the website and in the API.
11. **N11 The referral deadlines report shows another caseload's attached referrals** to caseload-limited staff.
12. **N12 Choosing an offered time on a reschedule moves only the time.** The offered instructor, place and remote setting are ignored, and the real instructor's calendar is never checked.
13. **N13 QuickBooks: a payment sent from here whose reply was lost is imported back as a second payment.** This is a remaining path of the earlier H2 finding.
14. **N14 Software update skips older pending database changes** when the database is already behind its files.
15. **N15 Converting a referral in the apps always fails when the person agreed to texts.** lastInsertId is read after an UPDATE.
16. **N16 The app's client save has no stale-form check.** The M12 fix was made only on the website. A stale app form reopens a closed case or undoes a reassignment.

# Appendix: findings by area

## Area: diff-server

### diff-server: server-side changes v4.26.0 → v4.27.0

#### [Medium] Microsoft auto-provisioning still admits guest (B2B) accounts that 4.27.0 now refuses to match by email
- Where: public/sso.php:178-198 (provisioning branch), compare public/sso.php:150-151 and public/inc/security.php:100-111 (sso_email_match_allowed)
- What happens: 4.27.0 says only a member of the organisation (`acct` = 0, own `tid`, no foreign `idp`) is trusted by email. But when `auto_provision_group` is set, the code checks none of those claims before it creates an account. A guest invited into the tenant (a vendor or a counselor from another organisation), whose email matches nobody here, signs in with Microsoft. They get a new active account in the auto-provision group, with that group's permissions, client records included, and are signed in straight away. The same identity would be refused if an account with that email already existed.
- Fix: before the INSERT, require `sso_email_match_allowed($claims, $issuer)` (or at least `acct` = 0 and no foreign `idp`). Otherwise refuse with SSO_EMAIL_MATCH_REFUSED_MSG.
- Status: CONFIRMED (code traced). It only applies when an administrator has turned on auto-provisioning.

#### [Low] Signed documents still show a "Withdraw" button that can never work
- Where: public/signatures.php:116 (the button is shown for status 'Signed'), public/inc/signatures.php:230 (`AND signed_at IS NULL`)
- What happens: since 4.27.0 a signed document cannot be withdrawn, but the staff list still renders "Withdraw <title>" for every Signed document. Pressing it always gives the error "Nothing was changed: this document is already signed…". For a JAWS user that is a dead control and an extra tab stop on every signed document.
- Fix: render the Withdraw form only for 'Awaiting signature' and 'Waiting to be signed here'.
- Status: CONFIRMED

#### [Low] SSO failure-log cap never trips when trust_proxy is on (audit IP vs client_ip mismatch)
- Where: public/sso.php:47-48 (counts `audit_log.ip = client_ip()`), public/inc/core.php:1246 (audit() still stores `$_SERVER['REMOTE_ADDR']`)
- What happens: with `trust_proxy` on, audit() writes the proxy's address on every row, while sso.php counts rows for the real client address from X-Forwarded-For. The count is always 0, so the "at most 10 per address in 15 minutes" cap on unauthenticated `login.sso_fail` rows does nothing. A script that starts a sign-in and returns `?error=` in a loop can fill the audit log. Separately, every audit row then records the proxy address, not the person's.
- Fix: store `client_ip()` in audit(), or count with the same function that wrote the row.
- Status: CONFIRMED (code traced; needs trust_proxy on)

#### [Low] An administrator who loses their authenticator, with no other administrator, has no way back in
- Where: public/login.php:77-84 and 95-115, public/verify.php:26-36 and 168 (emailed codes refused for totp accounts), public/reset.php:74-80 (a reset keeps TOTP), public/users.php:191 (the only reset)
- What happens: since 4.27.0 an account with TOTP can finish sign-in only with the app or a passkey. The only reset is another administrator on Users. A one-administrator agency whose administrator loses the phone, with no passkey, is locked out of every admin function. The emailed code (the earlier fallback) and "Forgot password" no longer help, and no CLI or dist tool clears `totp_enabled`.
- Fix: ship a server-side recovery (for example a dist/ CLI script that clears TOTP for one account and is audited), or keep the emailed fallback for the last active administrator. Document it in the deployment notes.
- Status: CONFIRMED (code traced; this follows from the owner's M1 decision, but no recovery path exists)

#### [Low] Session reminder is never sent to a client email corrected after a "not valid" report
- Where: cron/session_reminders.php:115-122 and 175-181
- What happens: with the per-recipient columns, an unusable client address marks `client_reminded_at` (and, when staff succeed, `reminder_sent = 1`) on the first run, and administrators are told once. Staff then fix the address on the client's edit page before the session. client_edit.php does not clear `client_reminded_at` or `reminder_sent`, so the client never gets the reminder at the corrected address. Before 4.27.0 the session stayed unmarked and the next run reminded the fixed address.
- Fix: when the client email changes (client_edit.php, portal, app), set `reminder_sent = 0, client_reminded_at = NULL` on that client's upcoming Scheduled sessions. Or do not mark the client side for a bad address.
- Status: CONFIRMED (code traced)

#### [Low] Authorization import locks the whole training_tracks table for the import transaction
- Where: public/client_import.php:192-193
- What happens: the in-transaction re-check `SELECT id FROM training_tracks WHERE LOWER(TRIM(auth_number)) = ? LIMIT 1 FOR UPDATE` cannot use an index. Under REPEATABLE READ it scans and locks every row (and gap) of training_tracks, once per imported row, up to 2,000. Until the import commits, staff logging hours, editing tracks or generating invoices wait on those locks and can hit lock-wait timeouts.
- Fix: lock on an indexed key (a normalised auth_number column with an index, or `GET_LOCK('auth:'.lower(auth))`), or take a single short lock up front.
- Status: PLAUSIBLE

Checked with no defect found: the kiosk hand-over (GET/POST allow-lists, the thank-you page, back button, ping and passkey guards, manifest and icon need no session, no injected form fields); client_ip() use across the limiters; the login/verify limits and idem425 markers (success=1 rows, never in lockout counts; lock names under 64 characters); the authenticator-only paths on the web and in the API; the lost-phone wipe (every DELETE, count and listing of api_tokens filters wipe-pending rows; the auth query admits them past expiry; wipe_done); QuickBooks payment sync, removal and the forget-company reset; the client_edit loaded_at/orig conflict flow; merge hold carry and trash payload rewrite; the purge_trash and trash.php hold checks; release and survey unknown outcomes (web and API); the staging scrub, make_staging and backup secret lists; mig_4.27.0 and the new SQL on MariaDB 10.4+; session_epoch binding (every establish_user_session uses SELECT *). tests/full_schema.php passes locally.

### diff-apps (git diff v4.26.0 v4.27.0 -- ios android tests/ios_api_regression.py)

#### [Medium] iPhone: offline entries over 30 days old are deleted after an upload that never reached the server
- Where: ios/Sources/API.swift:1716 (`} catch { break }`) and 1733 (`expireQueue(owner:)`), plus the 5xx/429 and refused-redirect `break`s at 1701-1709
- What happens: an entry (a case note, or a signature kept offline) is saved with no signal. The phone is then off or offline for more than 30 days (leave, rural work). The app is opened with no signal, or while the server returns 5xx or a redirect. flushQueue tries the first entry, gets a network error and breaks out of the loop. It then still calls `expireQueue`, which removes every entry older than 30 days, so the work is deleted without ever being sent. The code comment says an old entry "that could be sent just now was sent, not dropped", but that only holds when the server was actually reached. The regression test covers only the 200 and 403 cases.
- Fix: run `expireQueue` only when the loop got through to the server (no network, 5xx or redirect break, i.e. `transient == nil` and no thrown error). Or expire only entries that have a `lastError` from the server.
- Status: CONFIRMED (traced)

#### [Low] Android: a refused session token is sent to the new server typed on Sign in
- Where: android/app/src/main/java/org/casemanagement/app/Api.kt:393 (`base` prefers `trialServer`), 691-698 (`checkRefusedSession`); ui/LoginScreen.kt:80 (`tryServer`) and 117 (a 60-second loop)
- What happens: server X refuses the session with a 401, so `expireSession` keeps the token as `refusedToken`. Server X also returns 401 for a deactivated user whose token is still in its database, so the token can become valid again. Staff then type server Y and pass the password step, and `tryServer(Y)` makes `base` point to Y. While the code step is shown (and after a failed or abandoned sign-in, because `trialServer` is never cleared), the LoginScreen loop calls `checkRefusedSession` every 60 s. That sends `me` with `Authorization: Bearer <X's token>` to Y. This is the same kind of leak that the iPhone's new RedirectGuard prevents. If Y answers `wipe:true`, the phone is wiped on another organisation's word.
- Fix: store the server address together with `refusedToken` and skip the check (or drop the token) when `base` is a different server. Clear `trialServer` when sign-in fails or on Start again.
- Status: CONFIRMED (traced)

#### [Low] iPhone: the same server with ":443" typed counts as a different server, and signing in removes everything
- Where: ios/Sources/API.swift:1097-1121 (`apiURL` keeps an explicit port), 1384-1387 (`finishSignIn` compares `absoluteString`), LoginView.swift:323-334
- What happens: the kept address is `cms.example.org` and staff type `cms.example.org:443` (or the reverse). The two give "https://cms.example.org/api.php" and "https://cms.example.org:443/api.php", which are not equal. The sign-in screen warns that entries for cms.example.org will be removed by signing in to cms.example.org (the same host name on both sides). After sign-in, `removeEveryAccountsData` deletes every account's offline entries, drafts and prepared documents. Android's `ServerAddress.apiUrl` drops 443 (4.27.0) and so does RedirectGuard.port, but the iPhone's apiURL does not.
- Fix: in `apiURL`, set `c.port = nil` when it is 443, so both spellings give the same address.
- Status: CONFIRMED (read; the URLComponents behaviour is standard)

#### [Low] Android: a remove after a half-finished SecureStore migration brings back the stale copy
- Where: android/app/src/main/java/org/casemanagement/app/SecureStore.kt:84-85 (migrate), 69-72 (`fileFor`), 99 (`remove`)
- What happens: during migration, the new file's commit succeeds and the main file's removal commit fails (the phone is nearly full; the main file is the larger one to rewrite). The key is now in both files, and `fileFor` correctly uses the main copy. A later `remove(QUEUE_KEY)` (clearIdentity(keepQueue=false) on a server change or wipe) or a `remove("cache.N.client.M")` (a 403/404 when the client left the caseload) deletes only the main copy. `fileFor` then falls back to the cms_queue or cms_cache copy, which is stale. The old server's queue comes back and is sent to the new server, or a client record that should have been removed is shown offline again. The next start does not fix it, because migrate only looks at the main file.
- Fix: in `remove` (and `putNow`/`put`), act on both `main` and `homeFor(key)` whenever the key is in main.
- Status: PLAUSIBLE (needs one failed commit)

#### [Low] iPhone: when the approved warnings changed, the server's instruction is shown inside the warnings
- Where: ios/Sources/ScheduleView.swift:1009-1017; the server text is from public/api.php:2258
- What happens: staff approve the warnings and send `authorization_ack_hash`, but the warnings have changed on the server since. The server replies "Authorization review: <warnings> These warnings are not the ones you approved, so nothing was booked. Review them and approve again to book." The app strips only " Review the track and explicitly approve…", so the sentence "These warnings are not the ones you approved…" is shown and read by VoiceOver as one of the warnings, next to the approval toggle. The error above it then says it again with the app's own instruction.
- Fix: read `authorization_warnings` from the refusal (the call now has a `refusal:` hook) instead of parsing the message, or strip both server sentences.
- Status: CONFIRMED (traced)

#### [Low] iPhone: hand back after an uncertain Sign closes silently when the status check fails
- Where: ios/Sources/DocumentsToSign.swift:678-692 (`stopWithoutSigning`)
- What happens: a Sign failed or got no answer (`signOutcomeUncertain`), and then staff hand back without signing while the `signature` check also fails. The task returns without withdrawing, which is correct, but says nothing. The view has already closed. Staff are not told that the document is still waiting to be signed and must be withdrawn by hand. Android's `withdrawUnsigned` says exactly that in this case. Before 4.27.0 the iPhone always withdrew.
- Fix: send back a message, as Android does ("could not be checked or withdrawn, so it is still waiting to be signed; withdraw it from Documents to sign"), through onSigned or the parent's announcement.
- Status: CONFIRMED (traced)

#### [Medium] Microsoft auto-provisioning creates staff accounts for tenant guests (bypasses the 4.27.0 M2 member check)
- Where: public/sso.php:184-204 (auto-provision branch); compare sso_email_match_allowed() in public/inc/security.php:100

- Fix: before provisioning, require `sso_email_match_allowed($claims, $issuer)` (acct 0, no foreign idp). Otherwise refuse with SSO_EMAIL_MATCH_REFUSED_MSG-style wording and audit it.
- Status: CONFIRMED (code path traced)
